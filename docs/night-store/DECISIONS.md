# 夜宵店四端收尾决定记录

## 2026-11-07 退押和历史记录补全

- 修复已有退押接口的资金一致性，不扩展高级自动退出流程。持久化每次申请及按原缴款的分配，处理中保留额度，只有渠道确认SUCCESS才扣余额和写退款流水；未知、超时和404保留原申请，使用相同渠道退款号恢复。网络调用不占店铺数据库锁。
- 后台必须传退押申请编号并保留未知请求，重复提交核对同一申请。已有库存、在途、待审损耗、履约中订单或售后必须先清算；金额超余额直接拒绝，不静默截断。多笔原缴款允许逐笔确认，页面分别列示确认、处理中、失败款项。
- 退押占用不能被判责扣除和备货并发消费；退款确认导致余额低于最低档时关店。押金缴纳创建单据共用店铺锁，退押处理中暂不新建缴款。
- 4项真实PostgreSQL退押专项通过，涵盖并发备货/扣除、处理中不落账、失败原号重试、未知和404恢复、多笔分配及分页；一项测试原先错误假设数据库无排序返回的顺序，已改为按原缴款逐笔核对退款号，保留全部业务断言。
- 用户订单从最近100条截断改为数据库分页，支持加载更多及失败重试；刷新与筛选使用请求代次防旧响应覆盖。订单收入改用实际佣金账本净额，后台今日商品销售额统一为营业日净额、排除配送费并扣已确认商品退款。
- 配送H5仅在显式本机隔离预览时提供模拟押金缴纳，固定楼长、固定店铺、独立schema再次校验，确认界面提示无真实扣款；微信原生支付仍单列未验证。

## 2026-11-06 退款一致性修复决定

- 发现旧实现先变更订单/库存/券/佣金，再尝试网关退款且吞掉异常，不能证明资金成功，属于本Goal核心缺陷。
- 新增持久NightRefund，一期沿用既有每单一次退款范围；稳定商户退款号、并发租约、请求/处理中/未知/成功/明确失败状态。成功后才进行业务资源结算；未知和处理中保留资源占用并查单，失败允许同号重试。
- 已送达商品退款回库需预留历史货值额度，避免网关确认期间额度被其他备货用完。新增预留纳入同店串行额度计算。
- 旧订单状态不能作为微信成功证明；迁移不伪造历史网关成功。真实历史账单核对单列微信外部验收，新逻辑用隔离适配器验证内部状态机。
- 用户端购物车改为账号与店铺双重隔离；旧版无账号归属的全局购物车不迁移给任一新账号，防串车。结算刷新最新价格，不静默减少缺货数量；空商品清单与未加载分开。
- 浏览器CDP的出站拦截方法不在工具允许列表，因此不修改工具权限，改用本机预览响应CSP限制外部请求；API预览另有HTTP/HTTPS/fetch出站白名单与空外部凭证。

## 2026-11-06 支付、券与统计

- 修复夜宵主动查单走白天订单凭证的错误，按夜宵订单原校区商户查单。预支付保存商户/AppID，回调与查单必须核对金额、CNY币种、商户和AppID后才落账；已支付后重复回调不再把取消退款单误转支付异常。
- 未支付关单后真正晚到账保留异常单，允许后台整单原路退款，原库存已经回补，不再生成无来源负佣金。
- 微信退款404不代表明确拒绝。保留原占用，保护期后使用相同退款号恢复可能未发送/断线的请求；经历未知结果后的配置故障继续保留占用。商户配置变化禁止把原退款发往另一个商户。
- 一期每单一次退款包含部分商品赔付、整单商品退款、仅退配送费；零元商品退回与仅退配送费必须记录不同的商品处理语义。零元订单可内部确认，无真实支付/退款请求。
- 夜宵券增加校区夜商品主档适用范围，空集合表示本校区全部商品；门槛与抵扣都只计算适用商品，配送费不抵扣。发放后锁定范围；暂停发放保留已领取用户的使用权益。领券同模板串行，防止限领和总量被并发突破。
- 下单增加账号级requestId及内容摘要，重试只返回原订单；购物车、地址和备注等内容变化不能复用同一标识。客户端网络结果未知时保留原请求，先核对原订单；已确认拒绝才释放本地提交意图。
- 购物车支付后只扣除对应订单数量，保留后来新增的商品，并按账号记录已消费订单，防止重查支付重复清车。
- 首页商品净销售额不含配送费，扣除成功商品退款；收入只计待结算与已结算，预计收入单列。收入汇总和趋势来自全月聚合，不受明细20条/100条限制，支持月份、状态和分页。
- 营业日按已配置跨午夜场次的结束时间划界，非跨午夜按自然日；不再固定凌晨06:00。跨期佣金冲回进入调整月份和下一待结算批次，不改已出账批次。
