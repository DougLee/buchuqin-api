# API 需求对齐说明

对比基准：

- `buchuqinshishe-userweapp/docs/API_REQUIREMENTS.md`
- `buchuqinshishe-fulfillmentweapp/docs/API_REQUIREMENTS.md`

本轮原则：继续使用内存 Mock，不引入数据库或真实微信/对象存储依赖；优先保证两个小程序的 MVP 主链路与接口边界正确。

## 本轮已完成

### 用户端

- 保留首页、商品、购物车、预结算、订单、支付 Mock、售后、退款和消息现有接口。
- 新增购物车单项新增、修改、删除和清空接口。
- 新增地址编辑、删除、设为默认地址。
- 新增当前校园可服务楼栋列表。
- 新增结算可用优惠券及不可用原因。
- 新增确认收货。
- 新增售后详情、撤销售后及退款详情。
- 新增消息全部已读和未读分类计数。
- 订单详情查询也会触发 15 分钟支付超时关单，避免绕过订单列表直接支付。
- 地址、订单、售后、退款、消息均继续按当前 Token 用户隔离。

### 履约端

- Mock 登录可根据 `fulfillment-mock` 签发员工 Token。
- 普通用户 Token 禁止访问 `/fulfillment/**`。
- 增加员工在线/暂停/离线状态和签到、签退、当前班次接口。
- 任务返回 `availableActions[]`，供前端按服务端状态机渲染按钮。
- 增加独立的接单、取货、出发、到楼、交接、接货、楼内配送、送达和异常接口。
- 通用 Mock Action 路由继续保留，以兼容当前履约小程序。
- 取货要求包裹码，交接要求交接码，送达要求图片和定位。
- 状态动作增加前置状态校验，阻止越级履约。
- 增加请假提交/撤销、调配邀请查询/接受/拒绝。
- 增加当日绩效接口。
- 新增履约服务单元测试，覆盖非法迁移、扫码要求、员工状态和调配幂等。

## 暂不实现及原因

以下接口已在两端需求文档中保留，但本轮没有伪装成“真实能力”：

| 能力 | 原因 | 接数据库/平台时的实现建议 |
|---|---|---|
| 微信正式登录、手机号授权、Token 刷新 | 需要微信 AppID、密钥及开放接口 | 独立 AuthService，保存 openid/unionid 与 refresh token |
| 微信预支付与支付回调 | 需要商户号、证书、回调地址 | 独立 PaymentModule，支付单和订单状态分离，回调幂等 |
| 图片上传 | 需要 COS/OSS/本地文件服务选型 | 独立 FileModule，限制 MIME、大小并返回持久 URL |
| 仓库库位、逐件扫码拣货 | 当前没有仓储端页面和库存数据库 | 独立 Inventory/Picking 模块及库存流水 |
| 实时事件 WS/SSE | 当前 Mock 数据单进程可直接刷新 | 数据库落地后增加事件总线和客户端重连游标 |
| 隐私号与地图路线 | 需要第三方供应商 | 服务端代理供应商调用，避免密钥下发客户端 |
| 正式月结与打款 | 需要员工账户、审核和财务规则 | 独立 Settlement 模块，不以任务实时提成直接作为应付 |

## 上线前必须继续处理

1. 将金额从当前 Mock 的“元/小数”统一迁移为“分/整数”。
2. 数据库存储全部业务实体的 `campus_id`，查询层自动注入校园条件。
3. 删除生产环境的 `role` 查询参数；当前仅为一个小程序内快速切换三种角色而保留。
4. 将订单商品从完整 Product Mock 对象进一步收敛成不可变商品快照类型。
5. 为列表统一分页；当前用户订单和商品已分页，部分履约/消息 Mock 列表为兼容现有前端仍返回数组。
6. 接入审计日志、幂等键、任务版本号和并发库存事务。
